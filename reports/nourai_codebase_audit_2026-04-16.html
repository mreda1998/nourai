NourAI Codebase Audit

Generated on 2026-04-16 from the current workspace code only. README/spec/docs files were intentionally excluded from the analysis.

This repository already contains a meaningful product, not a stub. The implementation spans an Expo/React Native client, a FastAPI backend, a PostgreSQL/SQLAlchemy data layer, external product and food ingestion, a PubMed-backed ingredient research pipeline, and several user-facing intelligence surfaces such as ingredient deep dives, domain analysis, scan history, stack chat, and meal analysis.

Repo Shape

nourai/: Expo Router mobile app

backend-nourai/: FastAPI API, models, migrations, scripts

backend-nourai/scripts/: ingestion, research, enrichment, backfills

Audit Outcome

implemented Core scanning, search, product detail, ingredient intelligence, domain intelligence, stack/history, onboarding, auth, subscriptions backend, and data pipeline

partial Stack persistence on mobile, subscription UX wiring, account management, some route coverage

Executive Summary

  • The backend is the strongest part of the system. It has clear modules, schema evolution through Alembic, typed Pydantic contracts, Supabase-authenticated user profiles, and real service logic for products, personalization, USDA foods, stack logs, subscriptions, domain analysis, and AI meal/chat features.
  • The mobile app has a broad surface area and polished UI work, but several high-value flows still depend on local in-memory state rather than the backend. That creates gaps between what the API can do and what the app persists.
  • The ingredient intelligence architecture is more advanced than a typical MVP. Product ingestion links raw product ingredients to canonical ingredients, the research agent synthesizes PubMed studies into structured evidence, and product/domain scoring uses those stored signals rather than live LLM calls.
  • The biggest fixes are contract mismatches: guest scan auth, stack persistence mismatches, missing settings routes, subscription model drift, and biodomain naming drift on the product detail screen.

Implemented Features

Mobile App

  • Authentication with Supabase email/password and Sign in with Apple, plus guest continuation.
  • 10-step onboarding that captures biological sex, age range, pregnancy/breastfeeding, sleep, activity, diet, environment, product categories, focus areas, concerns, and goals.
  • Home screen with daily composite score, returning-user log summary, and scan CTA.
  • Product discovery/search by category, plus USDA food search merged into product search results.
  • Barcode scanning flow, meal photo analysis, and free-text meal analysis.
  • Product detail page with grade, bio-domain bars, ingredient list, nutrient deep-linking, personalization overlay, allergen callout, and add/remove stack actions.
  • Ingredient deep dive page with evidence summary, mechanism section, dose/safety, biodomain scoring, and found-in products.
  • Stack screen with radar chart, goal alignment, overlap detection, domain drill-down, AI chat modal, and meal log sheet.
  • History screen with grouped timeline and simple trend analytics.
  • Profile hub, health-profile summary, and settings pages for account, permissions, notifications, and subscription.

Data and Research Pipeline

  • Canonical ingredient model with synonyms, safety fields, evidence status, belief-vs-reality summaries, and precomputed domain effects.
  • Structured evidence records per ingredient/study with tags for user concerns and goals.
  • Per-ingredient biodomain score table with magnitude, direction, confidence, and dose-response metadata.
  • Research agent that searches PubMed, synthesizes studies with Claude, writes evidence rows, and computes biodomain impacts.
  • OpenFoodFacts ingestion, USDA nutrition fallback, unmatched ingredient logging, and multiple seeding/backfill utilities.

Architecture

Frontend Runtime Architecture

  • Navigation: Expo Router with a root stack and tab group.
  • Auth layer: Supabase session restoration in context/auth-context.tsx. The auth context also hydrates and syncs onboarding profile data to the backend.
  • App state: separate local AppStateProvider holding stack and meals in memory. This is fast for UI composition, but it is not the same as the persisted backend stack.
  • Networking: a central services/api.ts client auto-injects the Supabase bearer token when present.
  • Computation split: product/domain intelligence is mixed. Some screens use backend evidence-backed responses, while others compute local approximations from category/grade heuristics.

Backend Runtime Architecture

  • Framework: FastAPI application in app/main.py with CORS, typed dependency injection, and modular routers.
  • Auth: Supabase JWT verification via shared secret, with automatic user-profile creation on first authenticated request.
  • Persistence: async SQLAlchemy engine/session and Alembic migrations.
  • Layering: API routers call service classes, which rely on repositories for storage access. The separation is reasonably clean for an early-stage app.
  • Scoring and personalization: product/domain scoring reads precomputed evidence tables rather than calling LLMs synchronously during request handling.

Data Model Pattern

  • Product-centric: products and product ingredients hold the scan/search experience together.
  • Canonical ingredient-centric: ingredient intelligence is normalized into reusable ingredient records.
  • User-centric: user profiles store onboarding tags, stack entries, history, and subscription status.
  • Pipeline-centric: research and ingestion scripts continuously enrich the structured database rather than leaving intelligence trapped in prompts.

What Should Be Fixed First

Priority Issue Evidence Impact
P0 Guest barcode scan is effectively blocked for products fetched through /products/barcode/{barcode}. The mobile scan flow calls api.getProductByBarcode without requiring auth, while the backend barcode route depends on CurrentUser. Guests can enter the app and open the scanner, but a fresh barcode lookup can fail with 401. This undermines the core acquisition funnel.
P0 Product detail biodomain bars are using labels that do not match backend domain names. The product page expects labels like Dermal and Metabolic, while backend biodomain names are things like Skin & Appearance and Energy & Metabolism. Evidence-based biodomain values can silently collapse to zero on the product screen even when the backend computed them correctly.
P1 Stack persistence is split between local memory and the backend, and the contracts do not align. The app stores stack items in local React state keyed by product id, but the backend stack API is keyed by stack-entry id and returns stack-entry objects, not product cards. Signed-in users do not get a coherent cross-device or cross-session stack, and future backend wiring will be harder because current client assumptions are wrong.
P1 Profile hub links to missing routes. /settings/privacy and /settings/about are referenced, but those screens do not exist in nourai/app/settings/. Tapping those menu items will route to nonexistent screens.
P1 Subscription types/statuses drift between mobile and backend, and one mobile endpoint is missing server support. The mobile types expect premium_monthly, premium_annual, cancelled, and billing_issue, while the backend uses premium, canceled, and grace_period. The mobile client also defines /users/me/subscription/verify, which the backend does not expose. Premium UI logic and any future RevenueCat verification work can break or misreport status.
P2 Account and subscription settings are still mock flows. The account screen simulates save/delete, and the subscription screen simulates purchase/restore instead of calling a real billing layer. The app presents operational settings that are not truly functional.
P2 Onboarding exposes fewer goals than the rest of the system supports. The backend/domain/chat layers know about reduce_stress, better_sleep, and recovery, but the onboarding goal picker omits them. Users cannot fully drive personalization despite backend support.
P2 Backend tests are partially red because the suite parametrizes anyio for trio, but trio is not installed. pytest produced 17 passing tests and 3 errors, all from missing trio during the @pytest.mark.anyio food tests. CI reliability is weaker than it looks, and a basic dependency/config issue is masking test health.
P3 The dev mobile API base URL is hardcoded to a single LAN address and port. The client defaults to http://192.168.0.163:8081/api/v1, while the backend Makefile advertises local startup on port 8001. Developer onboarding and environment portability are brittle.

Recommended Next Moves

  1. Unify domain naming and stack contracts before adding more features. Those are foundational inconsistencies.
  2. Make scanning and stack behavior work equally for guests and signed-in users, with a clear persistence strategy.
  3. Finish or hide mock settings flows so the UI only advertises capabilities that are operational.
  4. Stabilize test execution by pinning the async backend strategy or adding the missing trio dependency.
  5. Replace the hardcoded mobile API fallback with environment-driven configuration.
